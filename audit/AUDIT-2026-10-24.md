# Audit — Richie Transport Services TMS

Independent review of the running system, not of a design.
Commit **`08d7177`**, branch `arena/368c3fd2-richie-rts`, 2026-10-24.

The previous pack in this directory (`AUDIT-REPORT.md`, findings `C-01` …) reviewed the
**browser-local prototype** at `030197e`, where the database lived in `localStorage`. That report is
now history: the system has a server, PostgreSQL and a sealed session cookie. This one tests the
build that exists today.

---

## 1. Verdict

The **write path is strong and the read path is not.** Every state change goes through one
authorised, validated, transactional command layer backed by real database constraints; every
change is refused for a role that lacks the permission, and refused by PostgreSQL itself when a
constraint is violated. That part of the system is better than most code of this size.

What is not there is the matching half: **the server sends the whole database to every signed-in
account.** Authorisation covers writes; reads are filtered only in the browser. A driver account
today can download every client, every other driver's trips, the user list and the audit log.

| Dimension | State | Note |
|---|---|---|
| Correctness of business rules | **Good** | 177 tests, command layer 100 % covered |
| Authorisation on **writes** | **Good** | every role 403s where it should (verified live) |
| Authorisation on **reads** | **Broken** | F-01 — full dataset to any session |
| Authentication | **Good** | Argon2id, sealed cookie, uniform errors, throttle *(bypassable: F-02)* |
| Database integrity | **Good** | exclusion constraint, append-only audit, monotonic odometer |
| Error handling | **Weak** | unvalidated payloads → 500 (F-03); no production log (F-04) |
| Observability / operations | **Weak** | no CI runs ever (F-06), no 500 logging |
| Performance | **Adequate now, bounded later** | 792 kB snapshot at 1 500 trips (F-05) |
| Accessibility | **Good basics** | skip link, landmarks, contrast measured; dialog semantics incomplete (F-13) |
| Documentation accuracy | **Fair** | several claims now false (F-14) |

Nothing found is exploitable by an anonymous visitor, and nothing found allows privilege
escalation. The two high findings are about the integrity of the *data already inside* the system.

## 4. The two that matter

### F-01 · Read authorisation is missing — the whole database goes to every session

`docs/PERMISSIONS.md` and `src/tms/scope.ts` describe own-record access: a driver sees their own
driver record, trips and vehicles; a client contact sees their own client, routes, roster and
rentals. `scope.ts` implements it, is covered by tests, and **is not imported by the application**:

```
$ grep -rn "scopeFor\|scopedView" src --include=*.ts --include=*.tsx | grep -v test
(no results)
```

`src/app/api/session/route.ts` returns `redact(database)` for any actor, and `redact()` blanks
passwords and nothing else. `src/app/api/commands/route.ts` returns the same full snapshot after
every write. The module's own header records the risk:

> this build has no server. … a production deployment must enforce the same rules in the API layer

The server exists now; that step was not taken.

**Measured.** A driver account created through the normal Users screen, signed in normally:

```
GET /api/session  →  795 770 bytes
role: driver
sees users: 2 | vehicles: 41 | clients: 2 | rentals: 0 | routes: 30 | trips: 1 500 | audit: 2 012
sample client name exposed: "Load Client"
```

Every trip (including other drivers'), every vehicle, every corporate client, both user accounts
with their email addresses, and 2 012 audit entries whose summaries name records and people.

**Why it matters.** The brief's own standard is that a role must not see data it is not entitled
to, and that the check must run where the caller cannot rewrite it. Today the check runs in a
browser, on a payload the visitor already has: the portal's filtering is a display choice, not a
control. This is also a data-protection finding — passenger and client contact data leaves the
server for accounts that have no business holding it.

**Fix (order of work).**
1. Add `scopedDatabase(database, actor)` in `src/server/` wrapping the existing `scopedView()` from
   `src/tms/scope.ts`, and apply it in **both** `redact(...)` call sites (session GET, commands
   POST) *after* redacting credentials.
2. Keep the actor's own row: a record-bound user must still see their own user record; a driver
   needs the vehicles and trips assigned to them, not the fleet.
3. Add an integration test per role asserting the *shape* of the payload (ids present / ids
   absent), not just the UI. The tests in `src/tms/scope.test.ts` already encode the expected sets;
   they need a second caller at the API boundary.
4. Delete the "HONEST LIMIT" paragraph from `scope.ts` once the server applies it, otherwise the
   comment will lie in the other direction.

**Severity note.** High, not critical: it requires a valid account, and it discloses rather than
corrupts. It is nevertheless the single most important defect in the build.

### F-02 · The sign-in throttle can be switched off by a request header

`clientKey()` in `src/server/api.ts` trusts `x-forwarded-for` unconditionally:

```ts
const forwarded = request.headers.get("x-forwarded-for");
const address = forwarded?.split(",")[0]?.trim() || ...
```

The production server is reached directly — there is no proxy to set that header — so the client
sets it. The bucket key is `address:email`; a new address means a new bucket.

**Measured** against the production build, one account, one password:

```
8 attempts, no header           401 401 401 401 401 401 401 401  → 429 on the 9th
3 attempts, rotating XFF        401 401 401        (unlimited: bucket never fills)
```

The control is therefore advisory. Anyone who reads the source has unlimited password guesses
against any account, at roughly 30 attempts per second (measured: 0.03 s per rejected attempt with
buckets empty; Argon2id cost only applies to a correct email).

**Fix.**
1. Key the bucket on the **email alone** in addition to the address, and require both to be under
   the limit. An email bucket cannot be forged, so the account is always protected even when the
   address is spoofed. (Spraying across many accounts is then limited per address, which is the
   right shape for a single-tenant deployment.)
2. Only read `x-forwarded-for` when an explicit opt-in is set — `TRUST_PROXY=1` in `.env`,
   documented in `docs/SETUP_AND_DEPLOYMENT.md` — and take the right-most untrusted hop, not the
   left-most.
3. Keep the in-memory store, but say in `docs/` that a restart clears it (it already says so in
   the module comment; it belongs where operators look).

## 5. The rest, with evidence

### F-03 · Command payloads are not validated (Medium)

`zod` guards the *envelope* (`type`, `password`, `input` as `z.record(z.unknown())`), never the
input itself. The command layer then dereferences fields and calls `.trim()` on them.

```
POST /api/commands  {"type":"create_user","input":{},"password":"a-password-123"}
  → 500  {"message":"The change could not be saved. The server log has the detail."}

TypeError: input.seatCapacity.trim is not a function
  at validateVehicle (src/tms/service.ts:269)
TypeError: Cannot read properties of undefined (reading 'trim')
  at validateSettings / validateOdometerReading / validateUser
```

Confirmed for `create_vehicle`, `create_user`, `update_settings`, `record_odometer`. The same
requests with **string** fields succeed (verified: `Vehicle GT-9001 added.`), so the UI — which
sends form strings — is unaffected; the defect is that the boundary accepts anything and turns a
client mistake into a server fault.

**Fix.** One `zod` schema per command in `src/server/commands.ts` (or a `record` of schemas keyed by
`type`), validated before the transaction opens; unknown keys stripped; numbers coerced from
strings, which is what the UI already sends. Alternatively, a top-level `try/catch` in
`executeCommand` that converts a `TypeError` into a 400 naming the command — cheaper, but it leaves
the boundary permissive.

### F-04 · A 500 in production writes nothing to any log (Medium)

`src/server/commands.ts:203` logs command failures **only outside production**:

```ts
if (process.env.NODE_ENV !== "production") console.error("[command]", ...)
```

So in the only mode an operator runs, the message "The server log has the detail" points at an
empty log. Verifying the F-03 failures required running the command layer outside the HTTP server,
because the running server had recorded nothing.

**Fix.** Log at `error` level in every environment — the command `type`, the error class and the
message, never the payload (it can contain personal data). If a structured logger is out of scope,
one `console.error` line is enough; silence is the worse failure.

### F-05 · Every response carries the whole dataset (Medium)

`/api/session` and every successful `/api/commands` return the complete snapshot, and the browser
has no incremental read.

```
GET /api/session   792 kB, 35–47 ms (1 500 trips, 41 vehicles, 2 012 audit rows)
POST /api/commands ~35–110 ms (same payload on success)
```

`AUDIT_LIMIT = 5 000` caps the audit rows; nothing caps trips, vehicles or documents. At three
years of daily busing (≈15 000 trips) the payload is roughly 8 MB per page load and per save, all
of it re-parsed and re-rendered. Nothing breaks at today's size — a single company's first year
fits — but the growth is linear and unmanaged.

**Fix (in order).** (a) Return only what the screen needs from `/api/session` once F-01 lands; the
scoped payload for a driver is small by construction. (b) Make the write endpoint return the
changed record plus the audit row instead of the snapshot, with the client patching its cache.
(c) If (b) is too large a change now, at least page the trip and audit collections and document the
ceiling in `docs/PROGRESS.md`.

### F-06 · The quality gates have never run in CI (Medium)

```
gh api repos/iwani1/Richie-RTS-/actions/runs  → total_count: 0
```

`.github/workflows/` contains `ci.yml` (typecheck, lint, coverage thresholds, build, integration
against real PostgreSQL), `codeql.yml` and `dependency-review.yml`. None has ever executed: `ci.yml`
triggers on `push: branches: [main]` and on pull requests, and all work has been pushed to a branch
with no pull request. Every "gates green" claim in this project, including mine, is a local claim.

**Fix.** Trigger on `push: branches: ["**"]`, or open the pull request that makes the branch
reachable. Then fix whatever the first run reports — the integration job has never been observed on
a GitHub runner and the workflow says so itself.

### F-07 · A scaffold screen ships in the product (Medium)

`src/routes.ts:46` adds `{ route: "documents", label: "Project brief", caption: "Source documents",
permission: null }`. `permission: null` means **every role sees it**, including driver and client
contact. It renders `src/docs/BriefDesk.tsx` — 512 lines, 8 % covered — whose class names
(`brand-mark`, `primary-nav`, `main-area`, `topbar`) do not exist in `src/index.css`, since the
stylesheet was rewritten for the Daylight redesign. It also writes review state to `localStorage`
(`richie-tms-doc-review`), which is the last surviving browser-persistence in the application.

This is the only visible remnant of the pre-redesign app inside the product, and it is reachable
from the sidebar on every screen.

**Fix.** Delete the route, the nav item and `src/docs/BriefDesk.tsx`. If the briefs are worth
keeping in the app, they belong in `docs/`, not in the sidebar.

### F-08 · CSRF protection is `SameSite=Lax` and nothing else (Low)

`POST /api/commands` with `Origin: https://evil.example` and a valid cookie is processed normally
(it reached business validation and was refused for a business reason, not a security one). Nothing
reads `Origin` or `Referer`.

`SameSite=Lax` does stop a cross-site form POST from carrying the cookie in current browsers, so
this is not exploitable today. It becomes exploitable the moment the cookie is relaxed (`SameSite=None`
for an embed, a proxy that rewrites the header), and the preview build already relaxes framing.

**Fix.** In the two mutating handlers, reject a request whose `Origin` header is present and not
equal to the request's own origin. Six lines, no library.

### F-09 · Password reset leaves sessions alive (Low)

Resetting a password updates the hash; the affected user's existing sealed cookie stays valid for
up to its 8-hour lifetime. Deactivation *does* take effect immediately (`findActor` requires
`active`), so account suspension is sound — only the credential change is slow.

The reset panel also tells the user *"The user's existing sessions are not revoked automatically in
this browser-local build"* (`src/screens/Users.tsx:238`), which describes a build that no longer
exists.

**Fix.** Add a per-user `sessionEpoch` to the session payload and compare it on each request (one
column, invalidated on reset), or shorten the TTL once F-01 makes per-request cost small. Fix the
copy either way.

### F-10 · No HSTS (Low)

`next.config.ts` sets `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`,
`Permissions-Policy` and a CSP — all verified present on `/`. Its own comment cites HSTS as a
reason for setting headers server-side, but `Strict-Transport-Security` is not in the list.

**Fix.** Add `max-age=31536000; includeSubDomains` **when serving over TLS only**; a blanket
`includeSubDomains` on a host that still serves plain HTTP will lock an operator out of their own
LAN address. This is the reason it was probably left out — make the condition explicit
(`if (process.env.HTTPS === "1")`) rather than omitting it silently.

### F-11 · CSP is looser than the application needs (Low)

Measured policy: `script-src 'self' 'unsafe-inline'` and
`style-src 'self' 'unsafe-inline' https://fonts.googleapis.com`.

Fonts are self-hosted (`@fontsource-variable/inter`, `@fontsource/ibm-plex-mono` imported in
`src/app/layout.tsx`), so the two Google origins are dead allowances that only widen the policy.
`'unsafe-inline'` for scripts is documented as a Next.js bootstrap requirement; that part is fair,
but it is the difference between CSP as a real second line of defence and CSP as decoration.

**Fix.** Drop `https://fonts.googleapis.com` and `https://fonts.gstatic.com` now. Add a nonce via
middleware when there is appetite for it (`D-49` already records this).

### F-12 · `Secure` cookies and plain-HTTP access (Low, deployment)

`secure: env().NODE_ENV === "production"` — correct — but a workshop deployment where staff reach
the app at `http://192.168.1.20:3000` cannot sign in: the browser refuses to store a `Secure`
cookie over plain HTTP. Chrome exempts `localhost` only. The failure is silent from the server's
point of view: the login returns 200 and the user stays on the sign-in screen.

**Fix.** Document it in `docs/SETUP_AND_DEPLOYMENT.md` §7 with the two correct answers — put TLS in
front, or run that installation with `NODE_ENV=development` on a trusted network and accept the
plain-HTTP posture knowingly. Do not silently drop `Secure`.

### F-13 · Panel dialogs are dialogs in name only (Low, accessibility)

`Panel` (`src/ui/primitives.tsx:273`) sets `role="dialog" aria-modal="true"` but does not move
focus in, trap Tab inside, restore focus on close, or respond to Escape. Tab therefore walks out of
the open panel into the page behind it, and a keyboard user can operate controls they cannot see.
The scrim is a full-screen `<button aria-label="Close panel">`, which adds a second "Close" to the
tab order alongside the header's `aria-label="Close"` — two controls named Close, one of them
invisible.

What is right: skip link, `<main id="main-content">`, `aria-current="page"`, `scope="col"` on table
heads, `role="status"` on busy indicators and filter counts, `aria-invalid` on inputs (added this
week), measured contrast on every token, and `prefers-reduced-motion` honoured.

**Fix.** In `Panel`: focus the first focusable element on mount, cycle Tab within the panel, close on
Escape, restore focus to the trigger, and make the scrim `aria-hidden` (keep the click handler,
drop the button semantics — or keep the button and remove the header one).

### F-14 · Documentation has drifted from the code (Low)

| Claim | Reality |
|---|---|
| README stack: "Docker/Podman Compose" | `docker-compose.yml` was deleted at the owner's instruction |
| README: "169 unit/UI tests" | 177 pass today; the number will drift again |
| README: "Zod at every request boundary" | only the envelope is validated (F-03) |
| `docs/PROGRESS.md:19` | references `docker-compose.yml` as a shipped artefact |
| `src/server/rateLimit.ts` header | cites `docs/SECURITY-NOTES.md`, which does not exist |
| `src/screens/Users.tsx:238` | "in this browser-local build" (F-09) |
| `src/tms/scope.ts` header | "this build has no server" (F-01) |

**Fix.** Replace fixed test counts with "the suite"; delete the compose mentions; either write
`docs/SECURITY-NOTES.md` or change the reference to `docs/DATA_PROTECTION.md`.

### F-15 · Coverage is uneven where it matters least (Low)

`77.08 %` lines overall. The command layer and permissions are at or near 100 %, which is the right
place to be. The holes are `Users.tsx` (0 %), `Registers.tsx` (4 %), `BriefDesk.tsx` (8 %) and
`Settings.tsx` (66 %); the four route handlers (`/api/session`, `/api/commands`, `/api/setup`,
`/api/auth/*`) have no tests at all — every finding above that needed a live server needed a live
server because of that.

**Fix.** The F-01 test belongs at that boundary and will pay for itself immediately. Delete
`BriefDesk` (F-07) rather than covering it.

### F-16 · The application role owns the schema (Low, database)

Migrations create the tables as the connecting role, so the app can `DROP TABLE audit_entry` or
`ALTER TABLE audit_entry DISABLE TRIGGER audit_append_only_trg`. The append-only guarantee is
therefore a guarantee against *bugs*, not against the process. For a single-workstation deployment
where the same person holds both roles, that is a defensible trade.

**Fix (if the deployment grows).** Two roles — `richie_owner` for migrations, `richie_app` with
`SELECT/INSERT/UPDATE/DELETE` only — and say so in `docs/SETUP_AND_DEPLOYMENT.md` §10.

### F-17 · `/api/health` says a little more than it needs to (Info)

```
{"ok":true,"service":"richie-tms",
 "database":"PostgreSQL 18.6 (PGlite 0.5.11); extensions: btree_gist, pgcrypto; migrations applied: 2"}
```

Unauthenticated. Useful for the operator, mildly useful for a visitor. Acceptable; consider
returning the version only when `NODE_ENV !== "production"`.

## 7. Plan

**Now — the two high findings, in this order.**

1. **F-01** read scoping at the API boundary, with a test per role. Everything else about this
   system's security claim depends on it.
2. **F-02** email-keyed throttle + `TRUST_PROXY` opt-in.

3. **F-03** payload validation (a 400 that names the field, not a 500 that names nothing).

## 8. Limits of this audit

- **No browser.** Accessibility was assessed from markup and stylesheet, not from a screen reader or
  a keyboard-only session. The claims in F-13 are about what the code does not do, which is
  verifiable; claims about how it *feels* are not made.
- **The database harness is PGlite** — one connection, WASM. Constraint behaviour matches
  PostgreSQL 18 and was exercised; timings and concurrency are not representative of a real server.
- **No penetration testing of TLS, the reverse proxy or the container.** Those were not in scope and
  are not in the repository.
- **The old `audit/` narrative** (`AUDIT-REPORT.md`, `DEMO-COMPARISON.md`, `findings.json`,
  `patches/`) describes the pre-server prototype. It is kept for history and is not a description of
  this build.
- I wrote most of this code. Treat the "what is good" section with the scepticism that deserves; the
  two high findings are reproduced by commands anyone can run.
